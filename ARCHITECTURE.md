# Architecture

## Overview

`proton-mcp` is an MCP facade over Proton Mail Bridge. It does not implement the Proton protocol and does not handle Proton mailbox encryption itself.

```text
                         trusted client
                              |
                              | MCP over authenticated HTTP
                              v
+----------------------------------------------------------------+
| Synology / Docker host                                         |
|                                                                |
|  +--------------------+     loopback IMAP     +--------------+ |
|  | proton-mcp         | --------------------> | proton-bridge| |
|  |                    |       127.0.0.1       |              | |
|  | MCP tools          |                       | Proton auth  | |
|  | IMAP adapter       |                       | + crypto     | |
|  +--------------------+                       +------+-------+ |
|                                                       |         |
+-------------------------------------------------------|---------+
                                                        |
                                                        v
                                                   Proton Mail
```

## Containers

### proton-bridge

Responsibilities:

- Authenticate to Proton Mail using Proton Mail Bridge.
- Decrypt/encrypt Proton mailbox traffic.
- Expose local IMAP/SMTP endpoints generated by Bridge.
- Persist Bridge state and its Linux secret-store/keyring data.

It is a separate container and separate lifecycle from `proton-mcp`.

### proton-mcp

Responsibilities:

- Connect to Bridge's IMAP endpoint.
- Expose narrowly scoped MCP tools.
- Validate all tool inputs.
- Bound output size and avoid bulk body retrieval.
- Eventually perform explicitly requested safe mailbox mutations.

It never needs the user's real Proton account password.

## Network boundary

The intended Compose design shares the Bridge network namespace with the MCP container. This lets `proton-mcp` reach Bridge at loopback while avoiding publication of Bridge's IMAP/SMTP ports.

Conceptually:

```yaml
proton-mcp:
  network_mode: service:proton-bridge
```

The only endpoint intended for client access is the MCP HTTP endpoint. Its exposure/authentication mechanism is deployment-specific and must be documented before production use.

## Credential boundary

There are two credential classes:

1. **Proton account credentials** — used only during Bridge authentication/bootstrap and never consumed by `proton-mcp`.
2. **Bridge IMAP credentials** — generated by Bridge and consumed by `proton-mcp` to access the local mailbox interface.

Neither class belongs in Git, container images, logs, or public environment examples.

## Data flow

For a typical `search_mail` request:

1. MCP client invokes `search_mail` with bounded filters.
2. `proton-mcp` validates the request.
3. The IMAP adapter translates filters into IMAP operations against Bridge.
4. Bridge communicates with Proton and exposes the mailbox result.
5. `proton-mcp` returns compact message metadata only.
6. A message body is fetched only if the client later calls `get_message` for a specific result.

This metadata-first design reduces latency, model context usage, and accidental disclosure of mailbox content.

## Version roadmap

### Implemented read-only tools

- `list_folders`
- `mailbox_stats`
- `top_senders`
- `mailbox_inventory`
- `cleanup_candidates`
- `mailbox_analysis`
- `search_mail`
- `get_message`
- `extract_receipt`
- `receipt_candidates`

### Implemented controlled writes

- `mark_read`
- `mark_unread`
- `archive_messages`
- `copy_messages`
- `move_messages`
- `trash_messages`

Write tools use opaque ids returned by read-only search tools, enforce a maximum
batch size, validate mailbox UIDVALIDITY, and support dry-run requests. Archive,
move, copy, and trash operate through Bridge's IMAP folder model; permanent
deletion is not exposed.

Write tools must operate on explicit message identifiers or a previously reviewed bounded selection. Permanent deletion remains out of scope initially.

### Cleanup workflow state

`create_cleanup_plan` persists an immutable, 15-minute plan containing explicit
opaque ids and a hash of a one-time confirmation token. `apply_cleanup_plan`
claims the plan before changing mail. A process interruption after a claim is
marked for review rather than retried automatically, because the remote IMAP
outcome may be unknown.

Completed plans create a compact operation record. For move-like operations,
the record contains destination opaque ids only when Bridge reports a complete
UIDPLUS source-to-destination mapping. Only those records can be undone through
`undo_cleanup_operation`; copies and operations without a complete mapping are
not presented as reversible.

### Manual automation rules

Automation rules are persisted in the same private state file as cleanup plans.
They match bounded mailbox metadata and are disabled by default. A rule has no
background scheduler: `prepare_automation_run` evaluates it manually and creates
the existing confirmation plan from the exact current message ids. Rule-run
history records no-match, pending-confirmation, applied, and needs-review states.

## Non-goals

- Reimplementing Proton Mail Bridge.
- Exposing arbitrary IMAP commands as MCP tools.
- Exposing arbitrary shell commands.
- Bulk downloading full mailbox contents into an LLM context.
- Permanent deletion in the initial releases.
- Sending email in the initial releases.
